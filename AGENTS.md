# Forever Goal Tracker: shared project rules

Shared rules for Codex and Claude, approved 2026-10-16. Historical reports are
evidence, not task assignments. Current user instructions take precedence.
Do not revive retired features or old "next session" tasks without a current request.

## Scope and efficient work

- Read-only requests do not trigger pulls, syncing, artwork inventories, builds,
  diagnostics or unrelated validation. Read only what the question requires.
- For implementation, continuation or project-status work, read
  [CURRENT](reports/CURRENT.md) once. Load only applicable references below;
  do not reread unchanged instructions within the same session.
- Prefer `rg` with explicit files or scoped globs. Bound output. Avoid scans of
  artwork, research data, caches and nested worktrees unless needed. Batch small
  independent reads.
- Preserve unrelated changes. Keep patches narrow and preserve encoding/line
  endings. Never stage, discard or overwrite another session's work implicitly.
- Explain outcomes briefly and clearly. Karl is a designer. No em dashes in copy
  or responses. For unseen visual glitches, measure before speculative fixes;
  after two failed attempts, stop guessing and propose instrumentation.

## Live checkout and progress safety

- This repository is loaded by the game. Determine PC versus Mac from the working
  directory before platform commands. Lua changes need `/reload`; new or replaced
  cached textures/fonts need a full restart. Report native tests not run.
- SavedVariables are local to each machine, not Git-synced progress. Do not edit,
  reset or migrate live saves as a side effect of development or testing. Preserve
  the old `KarlClassicGoals.lua` backup and separate older Era installation unless
  Karl explicitly requests work on them. Use isolated fixtures for automated tests.
- Preserve goal IDs, rule scopes, group ordering and selected parts. Steps/parts
  are saved by position: structural changes require a one-time progress remap.
  Wording alone needs no migration. Never automatically untick earned progress.
- Route piece totals through `FGT.PieceProgress`; do not count both a piece and
  its materials. Guard DB reads before `ADDON_LOADED`. Demo/test helpers must not
  corrupt real progress; restore staged state when finished.

## Compatibility, taint and performance

- Support Classic Era and Forever (TOC interfaces 11509 and 16001). Use real Lua
  5.1 checks. Its limit is 200 active locals per function; Core's main chunk is
  close. Prefer scoped blocks or `FGT` state; define locals before first use.
- Use client-compatible wrappers such as `FGT.ItemInfo`, not removed legacy
  globals. Guard optional APIs; extend regression coverage for removed APIs.
- Never read statistics or other unsafe shutting-down game systems at logout.
  Preserve `FGT.loggingOut` guards for statistics/friends. `pcall` cannot catch
  an engine assertion.
- Never replace global `SetItemRef`. Preserve the `addon` chat-link route through
  EventRegistry and the secure post-hook for legacy `fgt:` links.
- Do not infer Forever gameplay rules from Era or API existence. Unverified
  Forever dependency gates remain disabled; verify individual edges before adding.
- `GearData.lua` is generated by `python3 tools/geardb.py` from the client tables
  (see the [database report](reports/Gear-Planner-database-2026-10-19.md)). Never
  hand-edit it; put hand-checked sources in `GearCatalog.lua` (`curated`) and keep
  class limits in sync with the game's skill table. Player copy uses " · " in
  source labels.
- Avoid per-frame allocations, especially `CreateColor`; reuse objects, debounce
  events and stop idle animation work. Inspect affected hot paths. Offline checks
  do not establish native CPU cost, rendering correctness or gameplay behavior.

## UI and player wording

- SIMPLE, HELPFUL, CLEAR. Use existing widgets, palette, fonts and layout helpers.
  Visible text uses the native Warcraft font; Cinzel Bold is for hidden tab-width
  metrics only. Respect animation preferences and reduced/off behavior.
- Steps begin with an action, keeping item/quest name, count and useful location.
  Put advice/drop chances in tips. Preserve prerequisites, costs, timing and
  class/faction restrictions. Preserve exact link tags and material-parser strings.
- Say `Unconfirmed` for uncertain Forever rules and `Source unknown` for missing
  sources; use `completes automatically` or `tracked automatically`. Use separate
  hints: `Shift-click: Link in chat` and `Right-click: Wowhead`.
- Preserve account-wide progress when filtering views. Keep NEW versus UPDATED
  semantics and client/faction visibility. New detail widgets join `detailParts`.

## Git, artwork and validation triggers

- Check Git status once at the start of a new editing session. Pull only when
  source freshness matters and the tree is safe; ask before pulling a dirty tree.
  Do not repeat status/pull without a relevant state change or final diff review.
- Do not auto-commit or push each small change. Sync `main` on explicit request or
  an agreed editing-session closeout/machine switch. Review intended changes and
  verify the pushed commit is on the remote before reporting synchronization.
- At a relevant editing-session closeout, inventory `Media/artwork` recursively,
  including ignored originals, once. Sync added/updated originals even if awaiting
  installation approval. Reuse that inventory unless assets change. Never silently
  commit deletions. Preserve originals/attribution; installation approval is separate.
- Documentation-only work: validate text, links, preservation and diff; no Lua
  suite. Runtime Lua/data/TOC changes: run `tools/check.py` after final relevant
  edits, with targeted regressions/native review as needed. API/hook changes also
  require Ketho/LuaLS checks. Do not repeat passing checks without relevant changes.
- No release without Karl's authorization. Before publishing or pushing a release
  tag: run Ketho WoW API (`ketho.wow-api`) plus LuaLS (`sumneko.lua`) diagnostics
  against supported clients, prove annotations loaded, retain results, fix actionable
  findings and explain verified client exceptions without broad suppression. Also
  run `python3 tools/check.py`, review hot paths and complete applicable native tests.
  Missing diagnostics block release; ordinary source commits/artwork sync may proceed.
- Version tags trigger CurseForge packaging. Publishing also requires the release
  reference's metadata, package, store-page and post-publication checks.
